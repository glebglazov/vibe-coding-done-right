1. Big picture

ELI5. App turns speech into text. To do that it must wake up a sleepy robot brain (the "model"). Waking robot brain take long time. While it wake up, you stare at a PREPARING screen and tap your foot. 😤

Whole project = stop making you wait, or at least make the wait feel like nothing.

Technical: the app runs on-device Parakeet speech models. First use after a cache purge forces the Apple Neural Engine (ANE) to specialize the model — a 15–50s grind that also slows the whole render server system-wide. Earlier commits (S5/S8/S10) moved probes off the wrong thread pool and added launch telemetry. This series (tasks 03–07) builds on task 01's Predicted Launch Verdict — a guess, made before launch finishes, of whether this boot will be fast or slow.

Two kinds of launch

2. iOS thread pools — the kitchen story 🍳

ELI5. Phone is a kitchen. Cooks = CPU cores. You have only a few cooks (say 6).

Swift has a rule: "a cook must never stand still." If a cook is waiting for the oven, they should go chop veggies, not freeze. This pack of busy-only cooks is the cooperative thread pool. Every async/await task shares it.

The trap: if a cook freezes while waiting (a "blocking" job — reading a giant file, talking to a slow gadget), that cook is wasted. Freeze enough cooks and the kitchen stops. Orders pile up. The app feels stuck. 🥶

The exact rule we follow

PoolForNever do
Cooperative pool
Swift concurrency, async/await, Task		CPU work that yields, short non-blocking stepsBlock it (sleep, blocking read, sync syscalls). Task.detached does not escape it.
GCD / dispatch queue
our withBlockingTask helper		Blocking syscalls, big file reads, slow daemon connects—
Main actor
the one UI thread		UI onlyBlock it ever. A frozen main = frozen app.

Project memory documents three separate real bugs from breaking this rule: ActivityKit Activity.request (~8s, pins main), haptic daemon connect (~11s, pins main), and the cooperative-pool starvation freeze. ADR-0003 codifies "no blocking I/O on the cooperative pool."

3. The 5 commits, one by one

All five are AFK tasks, all done ✓, all build on the Predicted Launch Verdict from task 01.

03 · Timebox the prewarm barrier warm only

ELI5. Before, the app waited for the microphone to fully warm up before waking the robot brain — even when the brain was already awake and the mic warm-up was being slow (Bluetooth, headphones — up to ~20s!). So a fast launch got held hostage by slow mic prep it didn't even need. Now, on a predicted-warm launch, we set a timer: "wait a bit, then go ahead anyway." Mic keeps warming in the background; nothing cancelled.

Technical: the coordinator barriers on prewarmIfPermitted before the encoder load (ADR-0001 ordering). On predicted-Warm, waitForPrewarmBarrier races the prewarm task against a 2s timeout (predictedWarmPrewarmBarrierTimeout) via two Tasks into one CheckedContinuation, guarded by a lock-protected PrewarmBarrierContinuation so only the first wins. Predicted-Cold keeps the unbounded await prewarmTask.value. Timeout logs [InitTiming] …barrier timed out after 2000ms; continuing to encoder while prewarm remains in flight. ADR-0001 consequences amended. (+65/−2 in RecordingFlowCoordinator.swift, +91 tests)

04 · Decouple perceived readiness from model load biggest UX win

ELI5. Secret: you could already hit record before the robot brain finished — audio gets saved and the text catches up later. But the screen still showed PREPARING and hid the button until the very end. Dumb! Now, if the model files exist on disk, we show the ready screen immediately with a tiny "warming…" spinner. You can record from the first frame. PREPARING now only appears when there's a real download to wait for.

Technical: hero UI shows the ready state from first post-shell frame for any verdict except Cold Download, with a subtle warming indicator until Transcription Readiness lands. A record tap during warming runs Arming → Capturing normally; transcription catches up at Finalizing. New CONTEXT.md term added for the warming state (distinct from Arming and PREPARING). Perceived launch time no longer equals model-load time.

05 · Debug Logs reader hygiene

ELI5. The Debug Logs screen — the screen you open because things are slow — was making things slower. Every second it re-read a giant 20MB file, sorted the whole thing, and froze a cook (cooperative pool) doing it. So opening the debugger made the bug worse. Now it reads only the new lines since last peek, off the right crew, and shows a capped number of rows.

Technical: removed Task.detached blocking I/O → withBlockingTask (ADR-0003). Steady-state polling tail-appends only bytes since last position instead of whole-file read + sort each second; full re-read only on first load, window change, manual refresh. Rendered line count capped with a named constant to bound the LazyVStack diff.

06 · LogBuffer write batching

ELI5. Every single log line did a whole song-and-dance: open file, grab a lock, jump to end, write, measure size, close — and fought the keyboard extension for the same lock. Launch spits out dozens of lines at the busiest moment. Now lines wait in a little bucket and get poured in together every ~250ms under one lock. Way less thrashing.

Technical: lines append to pendingData; scheduleFlush() arms one DispatchWorkItem at flushInterval = .milliseconds(250). flushPendingLocked() takes withExclusiveFileLock once and writes the whole batch; size tracked by trackedFileSize counter (reconciled at flush) instead of per-line stat; LogBufferTrimmer streams the overflow trim instead of loading the whole 20MB file. flushPendingWrites() on backgrounding (AppDelegate hook). Cross-process merge with the keyboard extension stays correct — one lock per flush, lines still timestamp-sortable. A crash may lose the last unflushed window (acceptable for a debug log). (+138 LogBuffer, new LogBufferTrimmer, +58 tests)

07 · Background pre-specialization kills the cold grind

ELI5. The real fix for the scary 15–50s freeze: don't do it while you're watching. After a reboot / app update / OS update wipes the robot-brain's cheat-sheet (the ANE cache), iOS lets us run a chore while the phone charges overnight. That chore wakes the brain once, builds the cheat-sheet, and quits. Next time you open the app — already warm. You pay the cost when nobody's looking.

Technical: BackgroundModelWarmScheduler registers id glebglazov.vcdr-ios.parakeet-pre-specialization (Info.plist) and submits a BGProcessingTaskRequest with requiresExternalPower = true, requiresNetworkConnectivity = false. The handler runs BackgroundModelWarmRunner().run() (loads all four Parakeet models via ParakeetModelLoader with .cpuAndNeuralEngine), then re-schedule()s and sets setTaskCompleted; an expirationHandler cancels mid-load. Triggers live in BackgroundModelWarmTriggerStore (app-version / OS-version / reboot / actual Cold Specialize). No-ops if latest verdict already Warm. BackgroundModelWarmTelemetryRecorder + LaunchTelemetry surface warms in Launch History. (7 new files, +568/−12, +166 tests)

4. The trap we kept falling into

The same villain shows up in commit 05, ADR-0003, and three logged bugs in project memory: blocking work on the wrong pool.

It hides well because the code looks async. Task.detached { blockingRead() } reads like "this runs off to the side" — but Task.detached still lands on the cooperative pool. The cooks freeze. Rule of thumb the project now enforces:

blocking? (file I/O, syscalls, slow daemon connect, locks)
   └─ yes → withBlockingTask  (separate GCD crew)
   └─ no  → Task / async-await  (cooperative pool, fine)

UI? → main actor, and keep it featherlight
