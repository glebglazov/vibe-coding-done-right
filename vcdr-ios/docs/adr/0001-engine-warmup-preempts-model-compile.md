# Cold model specialization runs isolated behind a pre-warmed engine

On a cold launch the on-device transcription model's ANE specialization is left to grind, but it is **isolated** so it can starve neither the App Shell nor the audio engine: predicted-cold model loads run **serially with the heavy encoder last**, and the audio-engine HAL warm is **pre-paid before the encoder grind begins**. A record tap landing mid-grind arms the mic in ~hundreds of ms instead of ~18s, and the App Shell (settings, history, debug) stays usable throughout. We deliberately make the transcription model *slower to become ready* when a cold grind is expected in order to keep the mic and the shell responsive. Predicted-Warm launches are the exception: there is no ANE specialization to isolate, so the four model loads run concurrently and READY waits on the slowest load rather than their sum.

> **Amended.** The original decision here was "audio-engine warmup *preempts* the model compile via QoS demotion on record intent." That mechanism was never implemented, and device traces prove it could not have worked: an in-flight `MLModel(contentsOf:)` ANE load cannot be paused, and the contention is shared-resource saturation (ANE, audio HAL, render server), which scheduling priority does not relieve. The working mechanism is **ordering + isolation**, not priority. The QoS-demotion language below is retained only as a rejected option.

## Context

This extends the responsiveness-first tenet (`docs/architecture/rules.md`, Rule 11) and builds directly on ADR-0002 (shell-first) and ADR-0003 (blocking work off the cooperative pool).

The cold cost is the Parakeet **encoder** `MLModel(contentsOf:)` ANE specialization (`COLD_SPECIALIZE`): device traces clocked it at **15s on one launch and 52s on the next** (thermal-variable). The other three models are cheap — preprocessor/decoder/joint each load in 150–300ms even cold — so the encoder is the sole heavy load. Specialization starts automatically ~500ms after launch.

That single heavy load saturates **two independent shared resources**:

- **The audio HAL / mediaserverd.** A record tap mid-specialization took ~18s to start the engine: `AVAudioEngine()` construction, the lazy `inputNode` audio-unit init, `inputNode.outputFormat(forBus:)`, and `installTap` are blocking HAL calls that get starved by the concurrent ANE load (traced at 10s for `outputFormat`, 7s for `installTap`). The user saw a dead-looking "STARTING…" with no waveform, gave up, and got an Empty Result because no audio had been captured.
- **The render server / SwiftUI commit.** When the four model loads ran **in parallel** (a throughput optimization), the simultaneous ANE specializations starved sheet-presentation and view commits so hard that the record button never visibly flipped to Arming and the settings/history/debug controls felt dead — a direct violation of ADR-0002's guarantee that the App Shell stays usable while Transcription Readiness is pending. Device traces confirmed the asymmetry: when only the encoder was still loading (the cheap three already done), the Settings sheet presented fine; the freeze required *concurrent* heavy loads.

Off-main offloading (ADR-0003, `withBlockingTask`) prevents a hard main-actor *block* — and traces confirm the main actor kept servicing discrete tasks during the stall — but it does nothing about system-resource saturation. `.utility` QoS lowers scheduling priority without reducing the ANE/HAL flooding.

A Recording Run begins at the tap and moves through **Arming → Capturing → Finalizing** (see `vcdr-ios/CONTEXT.md`). Arming — the audio engine warming — must be short for the facade to stay honest, because the UI shows no timer or waveform until Capturing. If Arming takes 18s, the user stares at "STARTING…" for 18s.

## Decision

Isolate the encoder specialization on both axes by **prediction-driven sequencing**, not priority:

1. **Serialize predicted-cold model loads, encoder last.** `ParakeetProvider` loads preprocessor → decoder → joint → encoder serially when the Predicted Launch Verdict is `COLD_DOWNLOAD` or `COLD_SPECIALIZE` (was an unconditional four-way `async let` fan-out). This caps concurrent heavy-ANE work at one, leaving the render server enough headroom that the App Shell stays usable through the grind. The cheap three cost ~660ms serially — invisible, since the shell has already rendered and Transcription Readiness is deferred regardless.

2. **Pre-pay the engine HAL warm before the encoder grind.** The expensive engine work — `prepareAudioSession` + `prepareEngine` (construct, lazy `inputNode` init, `outputFormat`, `installTap`, `prepare()`) — runs *before* the encoder load starts, while the ANE is still idle, so it completes in hundreds of ms instead of being starved to ~18s. Crucially this work does **not** call `engine.start()`, so **no microphone indicator lights** — it is privacy-neutral. A record tap landing mid-grind then reuses the pre-prepared engine and pays only `engine.start()`.

3. **Parallelize predicted-Warm model loads.** The Predicted Launch Verdict is computed before loading from three persisted inputs: model artifacts on disk, the previous launch's actual verdict, and whether the device rebooted since that record. Only when artifacts exist, the last actual verdict was `WARM`, and no reboot is detected do we predict `WARM`. In that case `ParakeetProvider.loadCoreModels()` starts preprocessor, decoder, joint, and encoder concurrently on GCD. There is no cold specialization to isolate, so READY approaches the slowest individual load instead of the sum of four warm loads.

4. **Two-phase provider API orchestrated by the coordinator.** `ParakeetProvider` exposes `loadCoreModels()` and `finishWithEncoder()` (encoder + `AsrManager` on predicted-cold; `AsrManager` only after consuming the already loaded encoder on predicted-Warm). The coordinator runs the engine prewarm in parallel with `loadCoreModels()` and barriers on it before calling `finishWithEncoder()`. On predicted-cold launches this means the encoder can never start until the HAL warm is done. On predicted-Warm launches the API boundary and prewarm barrier still stand, but the encoder load may already be in flight because the prediction says no ANE grind needs isolation. The provider stays audio-ignorant; the coordinator owns the ordering.

The model finishing seconds later is invisible (it was always tens of seconds); the mic arming in hundreds of ms and the shell staying alive are not.

## Considered options

- **QoS preemption — demote the in-flight compile on record intent** (the original decision). Rejected: never implemented, and unimplementable as described — an in-flight `MLModel(contentsOf:)` ANE load cannot be paused, only reprioritized, and the bottleneck is ANE/HAL/render saturation that scheduling priority does not relieve.
- **Unconditional parallel model load** (four-way `async let`). Rejected for predicted-cold launches: maximizes throughput but is the direct cause of the App Shell freeze, because it runs up to four concurrent ANE specializations against the render server. Accepted for predicted-Warm launches, where persisted telemetry says the system specialization cache is already warm.
- **Eager `engine.start()` pre-warm at launch.** Still rejected: *starting* the engine lights Mic Presence (the system mic indicator) without the user recording — a privacy/UX regression. Note the distinction the original ADR missed: the HAL-expensive *preparation* (`prepareEngine`) is separate from `engine.start()` and lights no indicator, so pre-paying the preparation (decision #2) captures the latency win without the privacy cost.
- **Make the encoder itself faster / curtail specialization.** Out of scope here; this ADR is about resource isolation, not the encoder's intrinsic cost.

## Consequences

- **Transcription Readiness is deliberately deferred** behind the engine warm and behind a record tap's `engine.start()`. This is consistent with the documented Transcription Readiness model: audio is captured immediately; transcription catches up at Finalizing.
- **Launch-time `setActive(true)` must be verified on device** to confirm it lights no orange dot and does not disturb other audio playing when the app opens. The session is configured to mix, not interrupt (`.mixWithOthers`, A2DP retained, speaker-override only when no external output) — but the empirical check gates shipping decision #2.
- **Residual `engine.start()`-during-grind latency is to be measured**, not pre-optimized. The reuse path still pays a single HAL `start()` that the concurrent encoder may slow (expect ~1–3s, not ~18s). If it is still too slow on device, the only further lever is keeping the encoder from grinding during Arming — which trades back shell responsiveness.
- **First install stays slow once.** Before microphone permission is granted, the prewarm is skipped, so the very first record tap pays a cold engine build during the grind plus the permission prompt. One-time, accepted.
- **Do not re-parallelize predicted-cold loads or move the prewarm back to the init tail.** Both read as obvious optimizations and both reintroduce the freeze / long Arming this ADR exists to prevent. Predicted-Warm loads are allowed to parallelize because the persisted verdict says there is no ANE specialization to isolate.
- **Warm misprediction has one bad launch, then self-corrects.** A parallel load cannot be un-started. Reboot detection catches the common cache-purge case before loading, but storage pressure can purge the system CoreML/E5RT specialization cache without a reboot signal. If that happens after a `WARM` telemetry record, the next launch predicts Warm and starts all four loads concurrently even though the actual verdict is `COLD_SPECIALIZE`. The provider records the actual cold verdict and timings in launch telemetry after the load completes; the following launch then predicts cold and returns to serial encoder-last loading. This is detection-after, not abort.
- **Thermal variance (15s vs 52s encoder, multi-second pre-`async-let` launch gaps) is unaddressed** — it is a property of back-to-back cold specializations on a hot device, orthogonal to this isolation work.
