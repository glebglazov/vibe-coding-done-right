0. Why any of this exists

ELI5. Computer has a few cooks (CPU cores). One cook can only do one thing at a time. If a cook starts a slow job — wait for the oven, wait for a file, wait for the internet — and just stands there, your app freezes. 🥶

All these tools answer one question: how do I keep cooks busy and the kitchen smooth while slow stuff happens? Two big families:

  • old way GCD & friends — you, the boss, hand jobs to queues. Powerful, verbose, easy to deadlock.
  • new way Swift Concurrency (Swift 5.5, 2021) — async/await, Task, actors. The compiler helps. Code reads top-to-bottom even when it pauses.

They coexist. Real apps (like this one) use both — new way for most things, GCD when you must block.

1. Thread — the raw metal almost never use

ELI5. A cook. The actual person. You can hire one by hand (Thread { ... }) but it's like building your own oven from scratch — you manage its life, sleep, death. Nobody does this anymore.

Technical: Thread maps to an OS thread (pthread). Expensive (~512KB stack, kernel scheduling). Creating one per task doesn't scale — 1000 tasks ≠ 1000 threads. Every higher abstraction exists so you stop doing this. You'll see it only in old code, locks (NSLock), or Thread.isMainThread checks.

2. GCD / DispatchQueue — the old workhorse 2009

ELI5. Instead of hiring cooks, you write jobs on tickets and drop them in a queue. Grand Central Dispatch owns a pool of cooks and pulls tickets for you. You never see the cooks. You only choose which line a ticket goes in.

  • 🚶 Serial queue — one ticket at a time, in order. (A single cashier.)
  • 🏃🏃 Concurrent queue — many tickets at once. (A buffet.)
  • 🖥️ Main queue — the special serial line for the screen. UI only.

And two ways to drop a ticket: .async = "do this later, I'll keep going" · .sync = "I'll stand here until it's done" (⚠️ deadlock if you sync onto your own queue).

// hop off the main thread, do slow work, hop back to update UI
DispatchQueue.global(qos: .userInitiated).async {
    let data = loadBigFile()        // slow — fine, we're off main
    DispatchQueue.main.async {
        label.text = data.title       // UI — must be on main
    }
}

Technical: DispatchQueue abstracts a thread pool sized to the hardware. QoS (quality of service: .userInteractive → .background) tells the scheduler priority. Other GCD pieces you'll meet: DispatchGroup (wait for N jobs to finish), DispatchSemaphore (counting gate / crude lock), DispatchWorkItem (a cancellable ticket — used in this app's LogBuffer.scheduleFlush()), DispatchSource timers. GCD is not deprecated — it's the right tool for genuinely blocking work, because blocking a GCD thread only costs that one thread, not the whole cooperative pool.

🔗 In this codebase: withBlockingTask is a GCD bridge. When Swift-concurrency code hits a blocking syscall (big file read, slow daemon connect), it shoves that work onto a GCD queue so the shared cooperative pool stays free. See the kitchen "dishwasher crew" in the Launch Performance explainer.

3. OperationQueue — GCD with a brain 2011

ELI5. GCD tickets are dumb — fire and forget. An Operation is a ticket that's a real object: you can cancel it, check if it's running, and say "don't start B until A is done" (dependencies). Like a job board with arrows between cards.

Technical: Operation + OperationQueue sit on top of GCD. Add maxConcurrentOperationCount, addDependency(), KVO-observable state, and cancellation. Heavier than raw GCD. In new code, task groups + cancellation cover most of this more cleanly — but you'll still see OperationQueue in older networking/image-pipeline code.

4. async / await — the big shift Swift 5.5

ELI5. Old async code was "callback soup" — do thing, hand over a note for what to do when it's done, nest another note inside, and another… 🍝 Pyramid of doom.

await says: "pause here, let the cook go help others, wake me when the result is ready, then keep going." Code reads straight down even though it pauses in the middle.

// OLD: callback soup
loadUser { user in
    loadPosts(user) { posts in
        loadComments(posts) { comments in
            update(comments)     // 3 levels deep 😖
        }
    }
}

// NEW: straight line, each await = a pause point
let user     = await loadUser()
let posts    = await loadPosts(user)
let comments = await loadComments(posts)
update(comments)               // 😌

Technical: an async function can suspend at each await — it gives its thread back to the pool instead of blocking it. When the awaited result lands, it resumes (possibly on a different thread). The key mental shift: suspension ≠ blocking. A blocked thread is wasted; a suspended task is free. await is a marker of "a thread switch may happen here."

5. Task — a unit of async work Swift 5.5

ELI5. await only works inside async code. But your button tap is plain old sync code. Task { } is the doorway: "start an async job from here." It's one ticket dropped on the cooperative pool.

button.action = {
    Task {                                  // doorway into async
        let result = await fetchData()
        await MainActor.run { show(result) } // back to UI
    }
}

⚠️ The trap from the other explainer. Task.detached { } looks like "run this off to the side on its own thread." It is not. It still runs on the shared cooperative thread pool. If you put a blocking call inside it, you freeze a pooled cook — and enough of those starve the whole kitchen. Blocking work belongs on GCD (withBlockingTask), never in a Task. This exact bug is logged in this project's memory.

Technical: a Task carries priority, a cancellation flag (cooperative — you must check Task.isCancelled / call Task.checkCancellation()), and a result you can await via task.value. Task {} inherits the current actor & priority; Task.detached {} inherits nothing. The cooperative pool is capped near core-count on purpose — that's why blocking it is fatal where blocking a GCD queue is merely wasteful.

6. Structured concurrency — child tasks that can't escape Swift 5.5

ELI5. If you start 3 little jobs, who cleans them up if one fails or you cancel? Structured means child jobs live inside a parent scope — like kids on a field trip. The bus doesn't leave until all kids are back, and if the trip is cancelled, every kid comes home. No orphans.

  • async let — fire 2–3 jobs in parallel, await them later.
  • withTaskGroup — fire a dynamic number (a loop of them), collect results.
// async let — run two fetches at the SAME time, then combine
async let user  = loadUser()
async let feed  = loadFeed()
let screen = Screen(user: await user, feed: await feed)
// both ran in parallel; total time = the slower one, not the sum

// task group — N jobs, gather results
let thumbs = await withTaskGroup(of: Image.self) { group in
    for url in urls { group.addTask { await downloadThumb(url) } }
    var out: [Image] = []
    for await img in group { out.append(img) }
    return out
}

Technical: child tasks are bound to the parent scope's lifetime — the scope can't return until all children finish, and cancelling the parent cancels children (propagated, cooperative). This is what makes Swift concurrency safe vs. fire-and-forget GCD: no leaked work, automatic error & cancellation propagation. Use it instead of DispatchGroup for new code.

7. Actors & @MainActor — state without locks Swift 5.5

ELI5. When two cooks grab the same pot at once, food goes everywhere (a "data race" 💥). Old fix: a lock — a key only one cook holds. Easy to forget, easy to deadlock.

An actor is a pot with a built-in bouncer. Only one cook gets inside at a time, automatically. You don't manage a key — the compiler makes everyone await their turn. The pot's contents can never be touched by two at once.

@MainActor is the one special actor = the UI thread. Mark UI code @MainActor and the compiler guarantees it runs on screen-thread.

actor Counter {
    private var value = 0
    func increment() { value += 1 }   // safe — one caller at a time
}
let c = Counter()
await c.increment()                     // await: you wait for the bouncer

@MainActor
final class HeroViewModel {        // all its code runs on the UI thread
    var isReady = false
}

Technical: actors serialize access to their mutable state via an implicit mailbox — calls from outside are async (you may suspend until the actor is free). This replaces manual NSLock/DispatchQueue-as-lock patterns and is checked at compile time (Swift 6 strict concurrency flags races as errors). @MainActor is a global actor pinning work to the main thread — the modern replacement for scattered DispatchQueue.main.async. nonisolated opts a member out when it touches no actor state.

8. AsyncSequence / AsyncStream — a faucet of values Swift 5.5

ELI5. await gives you one value later. But some things give you a drip… drip… drip of values over time — location updates, log lines, notifications. An async sequence lets you for await each drip as it arrives, pausing between.

for await location in locationUpdates {   // loops as each new value arrives
    map.center = location
}                                          // pauses (frees thread) between drips

Technical: AsyncSequence is the async cousin of Sequence — for await suspends between elements. AsyncStream / AsyncThrowingStream let you build one from a callback or delegate API (push values into a continuation, finish when done). This is the Swift-concurrency answer to Combine publishers / NotificationCenter observers for many use cases.

9. Continuations — bridging old callbacks into await Swift 5.5

ELI5. Tons of old code speaks "callback": doThing { result in ... }. You want to await it. A continuation is a translator: it pauses your async code, hands the old API a callback, and when that callback fires it resumes you with the value. One bridge between the two worlds.

func loadThing() async throws -> Thing {
    try await withCheckedThrowingContinuation { cont in
        oldAPI.load { result, error in
            if let error { cont.resume(throwing: error) }
            else { cont.resume(returning: result!) }   // resume EXACTLY once
        }
    }
}

🔗 In this codebase: the prewarm barrier (commit 03) uses a CheckedContinuation to race a prewarm Task against a 2s timeout Task — whichever finishes first calls resume, guarded by a lock-protected wrapper so only the first wins. Resuming a continuation twice (or never) is a bug; the Checked variant traps on misuse. That's exactly the old→new bridge pattern.

10. Cheat sheet — what do I reach for?

I want to…UseFamily
Run async code from a sync place (button tap)Task { }new
Wait for one async resultawaitnew
Do 2–3 things in parallelasync letnew
Do N things in parallel, collect resultswithTaskGroupnew
Protect shared mutable stateactornew
Guarantee code runs on the UI thread@MainActornew
Consume a stream of values over timefor await / AsyncStreamnew
Wrap an old callback API in awaitwithCheckedContinuationnew
Do genuinely BLOCKING work (sync file read, slow daemon connect, locks)DispatchQueue / withBlockingTaskold
A cancellable delayed job (debounce/flush)DispatchWorkItemold
Hand-roll your own OS threadThread~never

The one rule that ties both explainers together

Is the work BLOCKING? (sync file I/O, syscalls, slow daemon, locks)
   └─ YES → GCD  (DispatchQueue / withBlockingTask)   ← old way, on purpose
   └─ NO  → Swift Concurrency  (Task / await / actor)  ← new way, default

Touching the UI? → @MainActor / DispatchQueue.main, and keep it featherlight.

Blocking the cooperative pool (Task / Task.detached with blocking work)
   = the bug behind the cooperative-pool starvation, the ANE freeze,
     and the haptic/ActivityKit main-thread stalls in this project.
